# שירות שליחת SMS לעובדים

שירות HTTP ששולח הודעות SMS לעובדי הארגון דרך ספק SMS חיצוני (המדומה שמסופק במשימה), שומר כל הודעה ב-SQL Server, מנהל את מחזור החיים שלה (Pending → Sending → Sent/Failed) ומאפשר לשאול על הסטטוס. כולל ממשק Angular פשוט.

- **Backend:** ASP.NET Core 10 (Minimal APIs), EF Core 10, SQL Server 2025
- **Frontend:** Angular 22 (standalone components, signals, zoneless), מוגש ב-nginx
- **בדיקות:** xUnit, FluentAssertions, NSubstitute, Testcontainers (SQL Server אמיתי)
- האפיון המלא שלפיו נבנה הפרויקט: [`SPEC.md`](SPEC.md). מסמך חלק ב': [`docs/PART-B.md`](docs/PART-B.md).

## API

| Method | Path | תיאור |
|---|---|---|
| `POST` | `/messages` | `{ "to", "body" }` + Header אופציונלי `Idempotency-Key`. `to` חייב להיות מספר של עובד במערכת, אחרת `400`. מחזיר `202` עם `{ id, status }` ו-`Location`. אותו מפתח עם אותו תוכן מחזיר `200` עם אותו `id`; עם תוכן שונה `409`. |
| `GET` | `/messages/{id}` | סטטוס ההודעה בלבד: `{ id, status, attempts, lastError, updatedAt }`. לא מחזיר נמען ותוכן, כי הדרישה היא סטטוס, ואין סיבה לחשוף את פרטי ההודעה לכל מי שמחזיק במזהה. `404` אם לא קיימת, `400` אם ה-id אינו GUID. |
| `GET` | `/messages?status=Sent` | עד 100 הודעות, החדשות קודם, עם הפרטים המלאים (נמען, תוכן, מקטעים, סטטוס, ו-`employees`: העובדים שהמספר שייך להם, יכולים להיות 0, 1 או כמה). `status` אופציונלי ולא תלוי רישיות. סטטוס לא קיים מחזיר `400`. התשובה עטופה ב-`{ items: [...] }`. |
| `GET` | `/health` | `200` כשה-API וה-DB זמינים, `503` אחרת. |

כל השגיאות מוחזרות כ-`ProblemDetails` (RFC 9457) עם `traceId`. שגיאות ולידציה מוחזרות כולן יחד.

## הנחות יסוד

1. **השדה `to` הוא מספר טלפון**, ולא מזהה עובד. זה נובע מהדרישה לוולידציה על "מספר טלפון" בקלט. מכיוון שהמערכת שולחת SMS **לעובדים**, המספר חייב להיות שייך לעובד אחד לפחות (בדיקה מול `EmployeePhones`); מספר תקין שאינו של עובד נדחה ב-`400`. מספר שמשותף לכמה עובדים מקבל הודעה **אחת**, והמערכת מציגה את כל העובדים שהמספר שייך להם.
2. **רק מספרי סלולר ישראליים.** הקלט מתקבל בפורמטים `050-1234567`, `0501234567`, `+972501234567`, `972501234567` (כולל רווחים וסוגריים), ונשמר בפורמט E.164 (`+972501234567`).
3. **אורך ההודעה: 1–670 תווים** אחרי Trim, שהם 10 מקטעי Unicode (עברית מחייבת Unicode: 70 תווים במקטע בודד, 67 בכל מקטע בהודעה מרובת מקטעים). מספר המקטעים מחושב ונשמר לצורכי מידע ותמחור.
4. **השליחה אסינכרונית.** `POST` שומר בסטטוס `Pending` ומחזיר `202` מיד. worker ברקע שולח לספק, כך שנפילה או איטיות של הספק לא מפילות את ה-API, וקריסה באמצע לא מאבדת הודעות.
5. **מזהה ההודעה הוא GUID** שנוצר בשרת, כדי שלא יהיה אפשר לנחש מזהים.
6. **נתוני העובדים נטענים מ-seed** (`Data/employees.seed.json`) בעליית המערכת. אין API לניהול עובדים, כי זה לא נדרש.
7. **ה-seed מגיע במבנה "מופעים"**, שורה לכל צירוף עובד+טלפון. בטעינה מאחדים את המופעים לעובד אחד עם כמה טלפונים. ה-seed בטוח להרצה חוזרת (לא יוצר כפילויות).
8. **אין אימות משתמשים ואין Deploy**, בהתאם למשימה.
9. **רק מופע אחד של ה-API רץ**, ולכן worker אחד מספיק. הרחבה לכמה מופעים מתוארת בחלק ב'.
10. **החוזה של הספק משוער** (לא נמסר): `POST {BaseUrl}/send` עם `{ to, message, reference }` שמחזיר `{ id }`, ו-`GET {BaseUrl}/status/{id}`. ההתאמה לשרת האמיתי נוגעת רק ב-`SmsProviderClient.cs`.

## החלטות

| החלטה | למה |
|---|---|
| **פרויקט API אחד** עם Minimal APIs ותיקיות לפי אחריות, ולא Clean Architecture | בהיקף כזה שכבות נוספות הן טקס בלי ערך. ההפרדה היחידה שחשובה היא `ISmsProviderClient`, כי שם צפוי שינוי (ספק שני). |
| **עובדים וטלפונים בשתי טבלאות** (`Employees` עם אינדקס ייחודי על שם+משפחה+כתובת, `EmployeePhones` עם אינדקס ייחודי על עובד+טלפון ואינדקס **לא** ייחודי על הטלפון) | אין כפילות של פרטי עובד, המפתח הטבעי נאכף ב-DB, וחיפוש "של מי המספר" מהיר. רווחים כפולים מכווצים לפני שמירה, כדי ש-"ישראל  כהן" ו-"ישראל כהן" יהיו אותו עובד. |
| **תור בתוך ה-DB** (polling על `Messages`) ולא Message Broker | ה-DB כבר קיים והטבלה היא מקור האמת, כך שאין מצב של "נשמר אבל לא נכנס לתור". `Channel` בזיכרון משמש רק כאות שמעיר את ה-worker מיד; אם האות הולך לאיבוד, ההודעה תישלח ב-poll הבא (תוך שנייה). |
| **מעברי סטטוס רק במתודות של `Message`**, ומעבר לא חוקי זורק `InvalidOperationException` | כל כללי מחזור החיים במקום אחד, קל לבדוק ולהסביר. |
| **`Attempts` עולה ב-`MarkSending`** (בתחילת הניסיון, לא בסופו) | קריסה באמצע שליחה נספרת כניסיון. בלי זה, הודעה שגורמת לקריסה חוזרת הייתה נשלחת שוב ושוב לנצח. מאותה סיבה: הודעה תקועה ב-`Sending` שכבר ניצלה 3 ניסיונות עוברת ל-`Failed` ולא חוזרת ל-`Pending`. |
| **retry רק ב-worker** (3 ניסיונות, backoff של 10 ואז 30 שניות), ו-HttpClient עם timeout של 5 שניות בלבד, בלי retry | מקור אמת אחד לניסיונות, שנשמר ב-DB ושורד קריסה. retry ברמת ה-HttpClient היה מכפיל את מספר הניסיונות בלי שה-DB יודע. |
| **סיווג שגיאות:** timeout, שגיאת רשת, 5xx ו-429 זמניות; שאר ה-4xx קבועות | 4xx אומר שהבקשה עצמה לא תקינה, וניסיון חוזר לא יעזור. |
| **ספק שמחזיר 2xx בלי `id`** נחשב שגיאה קבועה | ייתכן שהספק כבר שלח. ניסיון חוזר עלול לשלוח SMS כפול לעובד, וזה גרוע יותר מהודעה שמסומנת `Failed` ונבדקת ידנית. |
| **`messageId` נשלח לספק כ-`reference`** | אם הספק תומך בכך, הוא יכול לזהות כפילויות (למשל אחרי קריסה). |
| **בדיקת שחזור של `Sending` תקוע** בעלייה, ואחר כך פעם בדקה | בעלייה זה הכיסוי לקריסה. ההרצה התקופתית מכסה גם מקרה שבו השמירה האחרונה ל-DB נכשלה. עם מופע יחיד ו-timeout של 5 שניות, הודעה שנמצאת ב-`Sending` יותר מ-2 דקות היא בוודאות תקועה. **ידוע:** ייתכן שהספק כבר שלח, ולכן ייתכנו כפילויות (ראה חלק ב'). |
| **ולידציית טלפון לפי טווח הסלולר הישראלי** (`05X` + 7 ספרות), ולא לפי `IsValidNumber` של libphonenumber | libphonenumber משמש לפענוח ולפורמט E.164, אבל טבלאות ההקצאה שלו פוסלות בלוקים שנראים לו "לא מוקצים", כולל `050-1234567`, מספר הדוגמה של האפיון. הטבלאות האלה מפגרות אחרי המציאות (ניוד מספרים, בלוקים חדשים), ודחיית מספר אמיתי של עובד גרועה יותר מאשר לתת לספק לדחות מספר לא קיים. |
| **אותיות במספר נדחות** לפני libphonenumber | אחרת הספרייה ממירה אותיות לספרות ("vanity numbers"), ו-`050ABCDEFG` היה מתקבל. |
| **חישוב מקטעים GSM-7 כולל טבלת ההרחבה** (`€`, `[`, `{` וכו' נספרים כ-2) | כך החישוב תואם את מה שהספק יחייב בפועל. |

## מה לא נעשה ולמה

- **סטטוס מסירה (`Delivered` / `Undelivered`):** החוזה של ה-GET של הספק לא ידוע. `GetStatusAsync` קיים ב-`ISmsProviderClient` וממומש לפי החוזה המשוער, אבל ה-worker לא קורא לו. כדי לא להמציא ערכי סטטוס של ספק שלא ראיתי, החלטתי לא לממש את השלב הזה.
- **שרת ספק מדומה משלנו:** לא נבנה, בהתאם לאפיון. הבדיקות משתמשות ב-fake של `ISmsProviderClient`. לבדיקה מקצה לקצה בזמן הפיתוח השתמשתי בסקריפט זמני מחוץ ל-repo.
- **אימות, Deploy, CI/CD, Message Broker, Redis:** מחוץ להיקף במכוון.
- **API לניהול עובדים:** לא נדרש. העובדים נטענים מ-seed.
- **Pagination מלא:** יש רק הגבלה של 100 תוצאות. התשובה עטופה ב-`items` כדי שאפשר יהיה להוסיף pagination בלי לשבור את החוזה.
- **בדיקות Frontend ו-E2E אוטומטיות:** הממשק אופציונלי. בדקתי אותו ידנית ובסקריפט Playwright חד-פעמי.
- **ניטור ומטריקות:** יש רק לוגים מובנים. מה הייתי מוסיף מתואר בחלק ב'.

## מה הייתי מוסיף עם עוד זמן

1. התאמה לחוזה האמיתי של הספק, ו-polling של סטטוס מסירה (`Delivered` / `Undelivered`).
2. נעילת שורות ב-SQL (`UPDATE TOP(n) ... WITH (UPDLOCK, READPAST) OUTPUT`) במקום optimistic concurrency, כדי לאפשר כמה workers וכמה מופעים של ה-API.
3. מטריקות (OpenTelemetry): גודל התור, גיל ההודעה הוותיקה ביותר ב-`Pending`, שיעור כישלונות לפי סוג, latency מול הספק.
4. Circuit breaker מול הספק, כדי לא לשרוף ניסיונות כשהוא למטה.
5. Pagination מלא מבוסס cursor.
6. מדיניות שמירה (retention) ומחיקה/התממה של תוכן הודעות ישנות.
7. **שליחה לפי עובד:** אפשרות לשלוח לפי מזהה עובד (שם פרטי + שם משפחה + כתובת, שהם המפתח הייחודי) במקום לפי מספר. ההודעה תישלח לכל המספרים של העובד, אחרי הסרת מספרים כפולים (למשל אותו מספר שהוזן בכמה פורמטים, כמו `050-1234567` ו-`+972501234567`).
8. **Deduplication בקמפיין:** בשליחה לכמה עובדים בבת אחת, מספר שמשותף לכמה עובדים יקבל את ההודעה פעם אחת בלבד. את זה הייתי אוכפת גם במסד הנתונים, עם Unique Index על צירוף הקמפיין ומספר הטלפון (`CampaignId`, `To`), כך שגם בשליחה במקביל או בניסיון חוזר לא תיווצר הודעה כפולה לאותו מספר.

- **סטיות מהאפיון שהתגלו בזמן הפיתוח** ותועדו בטבלת ההחלטות: ולידציית הטלפון לפי טווח (בגלל `050-1234567`), `Content-Length` בבקשה לספק, ו-`Attempts` שנספר בתחילת הניסיון.
